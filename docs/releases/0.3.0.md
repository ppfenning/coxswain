# 0.3.0

Cut on 2026-09-06, hours after `0.2.0`. Every component is tagged `v0.3.0` in lockstep; `coxswain-tools`
is published to PyPI from that tag. Status: **beta**; nothing here breaks a `0.2.0` install. Almost every
change below was written and reviewed by the harness against its own repositories and merged by a person;
the defects it fixed were the ones costing it runs.

## coxswain-graphs

- A stale phase branch is rebased, or blocked by name, before the first task builds — twice in one
  morning a correct diff had been discarded at the end instead (graphs #52).
- A check that could not run is recorded as a harness fault carrying the command and the shell's answer,
  not as a failing build (graphs #56); check evidence is kept on failure and a patch is salvaged from the
  scratch tree when the model's recollection of it has drifted (graphs #51); a truncated patch is retried, not
  reviewed (graphs #55).
- An approved build that does not land is named in the exit summary with the command that re-applies
  it (graphs #58).
- A failed child dispatch leaves a record naming its intake item (graphs #57); the dispatch line (graphs #53); a
  decompose runs under the initiative's budget rather than a fixed node cap (graphs #50) and writes
  `initiative.md` with phase goals (graphs #54); the review entry point is one function (graphs #59).

## coxswain-tools

- `cox home`: leader, runs, backlog and attention in bordered panels, `ENTER` to drill in, `l` to land,
  `i` for intake, `t` for the conversation (tools #69, #73, #74, #75, #77, #84, #85).
- `cox runs top`: aligned columns, a TOKENS column, a COST column, NODE is the node running now, and the
  drill-down opens under the row (tools #70, #72, #76, #87).
- `cox route leader` gains `--pid` naming the durable process that owns the loop, refused when it is not
  alive, and a heartbeat primary (tools #71, #88, #90).
- `cox setup` gains a Roster tab; `enabled` is honoured by `setup install` and reported by the doctor
  (tools #79, #86); `cox route pull` is the first intake adapter (GitHub issues) behind a source interface (tools #82,
  #83); `runs land` treats unanimous approval as landable (tools #78); a window ceiling for pacing (tools #81); ruff
  docstring rules (tools #80). `pyproject` bumped (tools #89).

## coxswain-cartridges

- Style is guidance: the review charter notes a style departure and never withholds approval for it
  (cartridges #45); a `style_pass` role and skill make the edit after approval instead of sending the build back
  (cartridges #47, #51).
- `resolve_surfaces` refuses a work item whose surfaces are not real paths (cartridges #49); the decompose and
  intake-link skills state the rules the harness enforces (cartridges #48, #50); a seat's `enabled` must be a bool
  (cartridges #46).

## coxswain

`brew install ppfenning/coxswain/cox` on macOS; the formula installs `cox` alone and `cox install` fetches the rest (#30). The manifest documents the release (`tag`) and edge (`ref`) channels, never both on one entry (#29). Manifest and notes (#31, #32).

## Known gaps

- `cox dev release-check` reports drift that is not there on a clean tree (a doubled path in the manifest
  check; a comparison against generated CLI pages); until fixed, `cox dev release` needs
  `--allow-doc-drift`.
- The cartridge's configured checks run only `pytest` while every repository runs ruff in CI; six pull
  requests in one day were red for a rule the harness could not see.

## Components

All four code components carry changes; `coxswain-crew` is unchanged since `v0.2.0`.
