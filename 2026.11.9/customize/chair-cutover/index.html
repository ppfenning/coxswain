    Chair cutover

    This page moves the chair from the tick loop (cox chair run, the unit coxswain-chair.service) to the five queue workers (cox chair worker --kind <kind>, one unit each). It also covers how to move back. It is for the operator of the chair machine. The autonomous chair page explains what each kind does.

    Nothing is migrated. The workers read the same store rows as the tick, so the cutover stops one process and starts five. The rollback reverses that, and the tick needs nothing the workers wrote.

    Before the day

    Do these checks before the stop, on any day.

    1. Every machine runs a cox with the queue units (C6). Run cox chair status on each one. A cox that does not know the command is too old. Upgrade every chair and lane machine first, and any other machine whose profile could list chair.queues.
    2. The watchdog timer is installed and running on the chair machine. It is the check behind the workers: with every worker down it still pushes Chair queue down.
    cox chair watchdog --install      # writes the timer files and prints the lines that activate them

    Run the lines it prints. cox chair service --install --queues refuses, writing nothing, until the timer runs: on Linux systemctl --user is-active coxswain-chair-watchdog.timer says active, and on macOS launchctl print gui/$(id -u)/coxswain-chair-watchdog finds the agent loaded. 3. The notifier is set (notify: {ntfy: <url>} in the profile), so a worker's needs chair lines reach you. 4. The plans match on a copy of the real store (§5.3 step 3). Dump the live store, restore the dump into a throwaway database, and compare the tick with the workers against the copy:

    pg_dump -Fc -f /tmp/cox-store.dump "$LIVE_STORE_URL"
createdb -h <host> -U <owner> cox_parity
pg_restore -h <host> -U <owner> -d cox_parity --no-owner /tmp/cox-store.dump
cox chair parity --store-url postgresql://<owner>:<password>@<host>/cox_parity

    cox chair parity plans these, each a dry run that takes no lease and performs nothing: - the tick with chair.queues: []; - the tick with every kind listed; - each kind's worker.

    They run through a copy of your profile, in a scratch workspace. The last line is parity: match (exit 0), or parity: MISMATCH followed by what differs (exit 1). It is a mismatch when a worker plans more than the tick did, when an action is lost or planned twice, and when the tick with every kind listed still plans anything no worker plans: the tick is stopped at the cutover, so that work would be planned by no one.

    The command refuses the store your profile itself names. It compares what the store is, not its URL: the server's system_identifier (pg_control_system()) and current_database(), so another port, host name or query string onto the live database is refused too. A restored copy is another database and is accepted. It also refuses --workspace naming your own workspace. Drop the throwaway database afterwards. Stop on a mismatch: the workers would not do what the tick does. 5. The store's notifications work. cox setup doctor passes its store notify queue row. A worker wakes on a store notification and polls every 60 seconds as its fallback.

    The plan's §5.3 step 4 asks for a store_cursor whose per-table seq cox chair status would print. That cursor was not built: the workers wake on the store's NOTIFY and poll, so there is no per-table seq to watch, and the store notify queue row is the check that stands in its place.

    Preconditions for the stop

    All of these, at the moment you start:

    • Old-model work may be in flight. An initiative whose lane_model is task (or absent: task is the default) is the old model; phase is the new one. The old model's land slot (its lands, the fetch of an exited remote run, carries and closes) is the watch worker's. The tick runs each land as its own process (runs/chair-lands/), so a land it started before the stop finishes, and the watch worker collects it.
    • The tick's unit stops only its own process (Linux). A stop must leave a land in flight running:
    systemctl --user show -p KillMode coxswain-chair.service    # KillMode=process

    Any other value is a unit installed before the setting. Under the default, control-group, the stop in step 1 kills every land the tick started, since each one is still in the unit's cgroup. cox upgrade writes the line into the tick's unit file and the workers' template, and reloads systemd, before it restarts anything. Run it, then check again. The first edge upgrade onto this version runs the previous version's upgrade code, which does not write the line, so check after that one too. macOS needs nothing: launchd leaves a process in its own session running. - No land is in flight, as belt and braces. With the setting above a land outlives the stop, and the watch worker collects it. Still, start from a quiet runs/chair-lands/. A spec with no outcome beside it whose process is alive is a live land:

    cd <workspace_dir>/runs/chair-lands 2>/dev/null && for spec in *.spec.json; do
  [ -e "$spec" ] || continue
  [ -e "${spec%.spec.json}.outcome.json" ] && continue
  pid=$(python3 -c 'import json, sys; print(json.load(open(sys.argv[1]))["pid"])' "$spec")
  kill -0 "$pid" 2>/dev/null && echo "live land: $spec (pid $pid)"
done

    <workspace_dir> is the profile's. Wait until it prints nothing. No directory at all means no land has run. - No land is claimed. cox lander status shows no claimed item in the land queue. - The store was dumped within the hour. Keep the dump until the queues have run a day.

    The stop

    Five steps. The lander and every lane worker stay up throughout: they do not depend on the tick.

    1. Stop the tick.
    systemctl --user stop coxswain-chair.service           # Linux
launchctl bootout gui/$(id -u)/coxswain-chair          # macOS
    1. List every kind in the chair machine's profile (~/.config/agent-tools/profile.yaml), in the flow form:
    chair:
  queues: [housekeeping, watch, quarantine, decompose, launch]
    1. Install and start the five workers. The same command disables the tick's unit, so it does not come back at the next boot or login:
    cox chair service --install --queues --label <the chair's label>

    Linux gets one systemd template, ~/.config/systemd/user/coxswain-chair@.service, with five instances (coxswain-chair@housekeeping.service and the rest), and the tick's unit is disabled. macOS gets one launchd agent per kind (~/Library/LaunchAgents/coxswain-chair-<kind>.plist), and the tick's agent is booted out and disabled. The command refuses, writing nothing, unless chair.queues lists all five kinds and the watchdog timer runs. It is safe to run again: a file that did not change is not rewritten, and a running worker is restarted only when its file changed. Add --dry-run to see the files and the systemctl or launchctl steps first. It takes --environment-file and --profile as cox chair service --install does.

    If a step fails partway (a worker that does not start, say), the command puts the tick's unit back: it enables and starts coxswain-chair.service (on macOS, enables and boots in coxswain-chair.plist), and exits 1. The workers that did start keep running. The tick skips the kinds chair.queues lists, so it plans none of their work, but it holds the chair lease and raises queue_unowned for each kind that has no worker. Fix the failure and run the command again, or roll back.

    1. Catch up on what changed during the stop.
    cox chair worker --kind housekeeping --once

    This is one housekeeping pass now. Every pass re-derives its kind's work from the store's current rows, so the other kinds catch up on their first pass with no command. While the housekeeping unit already holds chair:housekeeping, the command stands by and exits 1 ("another worker holds chair:housekeeping"). That means the unit's first pass has run or is about to, so there is nothing more to do.

    1. Check.
    cox chair status
cox setup doctor

    cox chair status exits 0 when all is well: - each chair:<kind> line reads live, held by that kind's worker, with a beat a few seconds old; - the units read active on Linux and loaded on macOS; - there is no NOT RUNNING line.

    The chair lease (chair (the tick's lease)) reads expired or released once the tick has stopped. That is expected: no worker needs it.

    cox chair status prints no queue depth or oldest age, because there is no queue table to measure: each pass re-derives its kind's work.

    cox setup doctor should pass its required rows. Its units start row judges the units an upgrade restarts. After the cutover these are the five worker instances and the lander, and the tick's unit, now disabled, is not judged. An edge machine's scheduled upgrade restarts the five with the lander.

    Then release one small initiative and watch its run's exit reach its decision within seconds. The quarantine and launch workers wake on the runs and phase_queue writes.

    What raises the alarms now

    The tick used to raise queue_unowned <kind> when a listed kind had no live worker. With the tick stopped:

    • the first live worker in the order housekeeping, watch, quarantine, decompose, launch raises it for every other listed kind. Normally that is housekeeping. When housekeeping is the one down, the watch worker raises queue_unowned housekeeping;
    • the watchdog timer pushes Chair queue down for every listed kind whose lease has been dead longer than --stale-minutes (10), even with every worker down. With every kind listed, it no longer judges the tick's lease or status lines;
    • each worker pushes its own pass's needs chair lines and alarms. The stall alarm and the login and host checks went to housekeeping with the cutover.

    A hung worker does not look live. Each pass has a deadline: 45 minutes for watch, whose revert can wait half an hour on checks, and 15 for the rest (--pass-deadline). Past it the worker stops renewing its lease, so the lease lapses within a minute and the alarms above name the kind. A minute after that the worker exits with code 4, and its unit (Restart=always, launchd KeepAlive) starts a fresh one. A heavy watch pass can run past its 45 minutes this way; that is safe. The worker stops the checks and the git calls the pass was running, the fresh worker replans the work from the store, and the lands in flight keep running, since the units stop only the worker's own process (KillMode=process).

    What moved from the tick to the workers

    Every slot of the tick's plan has a worker, so the tick with every kind listed plans nothing (cox chair parity checks this):

    • watch owns the old model's land slot as well as the red-main revert: the lands, the fetch of an exited remote run, the deferred-land deadlock line, the carries and the closes. It runs each land as its own process in runs/chair-lands/, as the tick did, and collects the ones the tick started.
    • housekeeping owns the tick's loop chores, beside the stall alarm and the host checks. On each pass, while no tick holds the chair lease, it:
    • publishes the usage meter;
    • pulls the workspace (when chair.workspace_git is on, the default) and syncs each repo's checkout;
    • checks the lane hosts' checkouts;
    • applies the chat directives;
    • records the CI-gate pause line;
    • exports the board after its perform, which first fills the store from the workspace's files. This is how an intake filed as a file, or pulled in from the workspace's remote, becomes a row the decompose worker sees.

    Each chore is idempotent. The export runs only when the store or the workspace moved since the last one. - launch writes the why-not-launched reasons file beside the runs, since only its plan has those lines.

    The tick also restarted itself when its checkout moved on a development install. No worker does: the edge upgrade restarts the worker units.

    Rollback

    At any point after the stop:

    1. Take every kind out of chair.queues:
    chair:
  queues: []

    Each worker sees the change on its next beat and lets its lease go, so the tick can take every kind back. 2. Stop and remove the workers, and start the tick:

    cox chair service --uninstall --queues

    It stops and disables the five units, removes their files, and enables and starts coxswain-chair.service (on macOS, enables and boots in coxswain-chair.plist). It refuses while chair.queues still lists a kind, because the tick skips every listed kind and would plan nothing for it. That is why step 1 comes first. It is safe to run again. 3. Check that cox chair status shows the chair lease live, held by the tick, and that cox chair run status lines are coming in again. The chair:<kind> lines go to released or expired.

    The tick derives everything from the store's rows on each pass, so it needs nothing the workers wrote. No schema step and no restore. New-model initiatives in flight keep working either way.

    After a rollback the tick's runs directory keeps chair-queue-lease-seen, which makes the tick fail closed when it cannot read the worker leases. Once no worker will run on this machine again, delete it as the autonomous chair page describes.

    The tick loop stays in the tree until the queues have run two weeks without a rollback.
