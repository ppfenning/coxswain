    tools

    The cox command. This folder is the agent_tools package inside the coxswain repository; it ships as part of the one coxswain package. To install Coxswain, see the root README.

    Tools are what the agent seats run instead of spending tokens. Anything a seat would otherwise do by reading a file wholesale and reasoning about it — summing a run's cost, counting what a traced node did, cleaning up after a run, landing a branch — is a function here that reads it and answers.

    The mould, every time: a pure core with no I/O, the filesystem and the network at the edges, dry-run by default where a write is involved, and tests that never touch a real run.

    What is here

    agent_tools/   the package: the `cox` CLI, its command table, and every command's pure core and edge
tests/         this folder's suite
docs/          design notes and guides for single features (shared store, forgejo forge)
ops/           operator scripts that sit beside the CLI (store backup)

    Tests

    From this folder:

    cd src/tools && uv run pytest -q

    The Postgres cases in tests/test_run_store_backends.py run only when COX_TEST_POSTGRES_URL names a database where the test may create a schema. Without it they are skipped.

    Bare cox setup opens towpath; it needs a terminal and towpath, and otherwise points you at setup doctor and setup install.

    The route group reads one profile, ~/.config/agent-tools/profile.yaml (the directory keeps the deprecated agent-tools name), or the path in AGENT_TOOLS_PROFILE, or --profile PATH for one command. cox setup install and cox setup migrate point its harness_dir, skills_roots and umbrella_dir into the checkout. cox setup install points provider_profile at the shipped src/cartridges/providers/claude-code.yaml unless --provider-profile names another; a team's own provider profile lives outside the checkout, in <home>/providers/ or the workspace, and cox setup migrate keeps it. cox setup store --store files|shared picks the run store; see docs/shared-store.md. New to the profile? docs/getting-started.md walks through it.

    cox route sync resolves a repo only for the items it will act on: in the profile's tracker_scope and not already done or dropped. A settled item whose repo: no longer resolves is left out without a refusal. An open item whose repo does not resolve is refused by name and the sync goes on with the rest. The run prints route sync: skipped N item(s): <repo> (<count>) and exits 2 only when an open item was skipped. To keep a retired repo resolving, map it to its new slug in the profile; a key matches the repo: value or its last path segment:

    repo_aliases:
  agent-tools: ppfenning/coxswain
  coxswain-graphs: ppfenning/coxswain

    Under tracker_scope: epics or initiatives the board starts with open items only. A settled epic (done or dropped, or every task done or dropped) with no issue: never gets one, and the run prints route sync: left N settled item(s) without an issue. An item that already has an issue, hand-set or not, keeps syncing as before. Set tracker_backfill: true in the profile to create issues for settled items too. tracker_scope: all is unchanged.

    cox route sync --prune-out-of-scope --dry-run lists the open task issues and cards outside a narrowed scope; without --dry-run it closes each issue as not planned with a one-line comment and removes its card. Only unsettled tasks whose issue carries the coxswain label in the task's own repo are listed. A card is listed while that issue is labelled, open or closed, so a card left by a failed delete goes on the next run. An epic's issue, a landed task, and a task linked by hand to an unlabelled issue are never touched. A hand-added coxswain label counts as made by sync, so that issue is pruned too. Under all nothing is out of scope.

    Under a narrowed scope each sync rewrites a marked checklist block in a synced initiative's issue body, one line per task with its state and landed PR; text outside the block is left alone and no sub-issues are made. Under epics, a one-task initiative below the threshold with a Target release: line appears on one <version> fixes issue per release, with the same block. Its land PR says Part of #<that issue>, and a sync finds that issue by title, so it never opens a second. A one-task initiative with no target release stays in the store.

    Integrations that name a vendor (intake sources, forges, trackers) live in ppfenning/coxswain-plugins.

    Reporting to herdr

    cox runs herdr is a sibling of cox runs bar. It reads the same idle|running|attention class and reports it to the herdr pane it runs in, so the fleet shows in herdr's agent sidebar and notifications. Running maps to working, attention to blocked, idle to idle. Attention is a quarantine, a budget stop, a remote lane whose heartbeat is older than the chair's heartbeat window, or approved work not yet landed (the set cox runs stranded lists). The agent name is coxswain. The command sends on a state or label change plus a keepalive no more often than --interval, and calls pane release-agent with --source coxswain --agent coxswain when it exits. Outside herdr, with HERDR_ENV, HERDR_PANE_ID or HERDR_BIN_PATH unset, it prints one line to stderr and exits 0, so it is safe in any shell startup. A herdr call that fails is logged and the loop goes on.

    The rows are the ones cox runs top draws: local runs plus the remote lanes named by the shared store's leases and heartbeats. One adapter on the chair's machine therefore sees the whole fleet, and cox runs bar shares the same rows. Remote approved or quarantined runs show as blocked once the chair has fetched them. Do not run the adapter on lane hosts.

    A lane host that dies stops renewing its lease, and the lease lapses two minutes after the last beat, so the lane leaves the live set before its heartbeat looks ten minutes old. The rows therefore also include every lane whose lease lapsed without a release. Those rows read as attention, so the pane shows blocked until the lease is reclaimed or released. A clean exit releases the lease and drops the lane.

    Run this command in a pane, typed or as the pane's startup command in your herdr layout. herdr sets the three variables inside every pane:

    cox runs herdr --interval 10

    --once reports a single time, releases and exits. A short label such as 2 in flight, 1 to land travels as --message on pane report-agent, and a change of label alone sends a report. SIGTERM and SIGHUP, which a closing pane sends, release the pane like Ctrl-C.

    Maintainers

    Release and docs commands live in devtools/ at the repository root: run uv run --frozen python -m devtools <command> there. cox dev and cox release print that pointer and exit 2.
